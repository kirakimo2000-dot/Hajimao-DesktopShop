## 当前核心玩法

Hajimao DesktopShop 是传统桌面放置式挂机增量游戏。常态为吸附在任务栏上方的横向像素街区；街区只有一家店时只显示一家店的宽度，新增店铺后持续横向增长，不限制街区内容总长度。点击店面进入对应店铺挂机页。

0.2 系列已取消旧的进货、补货、货架、销货、员工职业和排班循环，改为自动战斗式招待：

1. 顾客按现实本地时段和当前运行事件，从不同刷新池进入店内。
2. 默认店员“毛毛”自动使用已装备的商品投向顾客。
3. 商品削减顾客的“需求值”；清空需求代表成功招待，不使用击杀叙事。
4. 成功招待获得现金，并随机掉落商品。
5. 首次掉落解锁商品；重复掉落自动提升精通。
6. 玩家为每家店配置 3～6 个商品槽位，比较招待力、攻击间隔、收益倍率和特殊效果。
7. 玩家用共享现金开设新店；每次扩张从候选店铺中选择，而不是按等级固定解锁店铺。
8. 不同店型具有不同的顾客压力、风险、客流和收益倾向。

玩家只应接触少量高价值选择。复杂收益、客流、掉落和事件算法在后台运行，但关键影响必须用短文本解释。不得重新引入大量运营表格或频繁维护操作。

## 不可违背的产品约束

- 没有游戏内时间。
- 没有离线收益；只有程序实际运行时获得收益。
- 没有暂停、倍速或“现实时间 1x”文字。
- 桌面挂机街区始终置顶；经营管理页不需要永久置顶。
- 桌面挂机窗口不显示普通任务栏按钮。
- 保留鼠标穿透功能；删除所有音效功能和相关菜单。
- 街区页不显示任务信息；特殊事件使用上方短弹窗。
- 窗口拖动后靠近任务栏自动吸附，并保留用户拖动的 X 坐标。
- 街区与店铺页跳转或拖动时必须调整到当前屏幕可见区域，重点保护较大的店铺页。
- 店内不再存在货架玩法，每个店只使用一张内饰背景图；现阶段允许占位图。
- 当前只有默认店员毛毛，无职业、无特殊效果。未来用角色与抽取区分，但 0.2.x 不实现抽卡系统。
- 所有人物动作使用严格 24 个逻辑帧；骨骼、皮肤、动作和角色数据分离，重点保证后续扩展。
- 人物移动、攻击与顾客轨迹必须有明确行为逻辑，不能只做无目的往返动画。
- 视觉为清晰像素风，场景精灵使用最近邻采样和整数像素定位。
- 优先玩法和可理解性，资源扩充与精美美术后置。
- 版本从 `0.1.0` 递进；当前属于 `0.2.x`，不要随意跳大版本。
- 每个大阶段写一次总结和下一步，小修改不重复写报告。
- 保持模块化、低耦合、按版本更新 `CHANGELOG.md`，及时清理工作区。
- 默认单智能体工作；没有明确并行收益或用户要求时禁止批量生成审查智能体。

## 技术栈与架构

- Windows 10 2004+
- .NET 10 / C# 14
- WPF 桌面外壳
- SkiaSharp 像素场景渲染
- SQLite JSON 状态载荷，当前 schema v8
- xUnit 自动测试
- GitHub Actions Windows 发布门禁

分层边界：

- `HajimaoDesktopShop.Domain`：确定性战斗、目标选择、冷却、投掷物、命中、招待、逃离、商品图鉴和装备规则。
- `HajimaoDesktopShop.Application`：现实顾客池、运行事件、掉落、精通、收益、多店参数、扩张和不可变快照。
- `HajimaoDesktopShop.Rendering`：只消费快照与事件，负责 Skia 场景、骨骼动画、移动插值、投掷物和反馈，不计算业务结果。
- `HajimaoDesktopShop.Desktop`：WPF 窗口、视图模型、输入与桌面交互，只发命令和展示结果。
- `HajimaoDesktopShop.Infrastructure`：JSON 内容、SQLite 存档、配置与诊断。

业务规则不得进入 XAML code-behind；Domain 不得引用 WPF、SQLite、SkiaSharp 或日志基础设施；禁止可变全局状态、服务定位器、视图直连仓储和循环项目引用。

## 0.2.1 与 0.2.2 修复记录

### 0.2.1

修复旧存档恢复时引用 `dish_soap`，但新版商品配置没有该键，导致启动直接抛出 `KeyNotFoundException` 的问题。恢复逻辑会清洗旧商品引用并保存兼容后的状态。

### 0.2.2

修复便携版进程和窗口句柄均已创建，但桌面挂机窗口完全透明、用户看起来像“没有启动”的问题。根因是透明 WPF 分层窗口与便携单文件/Skia 合成组合不可靠。`DesktopShopWindow` 已改为不透明 WPF 合成，同时保留无边框、置顶、不显示任务栏和鼠标穿透能力。

验证结果：全量测试 679/679 通过；GitHub Windows release 门禁通过；公开 Release 的 ZIP 资源已上传并可下载。

## 当前内容规模

- 24 种可收集商品。
- 12 类顾客。
- 4 个现实本地时段刷新池。
- 11 种运行事件修正。
- 24 个店铺/内饰映射，目前主要是轻量占位背景。
- 默认角色毛毛。
- 毛毛与顾客合计 10 类动作，每类 24 个逻辑帧。

这些数量只能验证数据驱动框架，不代表内容已经丰富。用户要求后续商品、顾客、店铺和事件资源必须充足，但在核心体验没有稳定前不要急着堆数量。

## 已知真实差距

1. UI/UX 与视觉引导仍明显不合格；信息层级、入口含义和首次操作目标不清楚。
2. 新玩家打开游戏后不知道该做什么，文字可能过多，但真正关键行动没有被突出。
3. 挂机正反馈不足；现金增长、首次掉落、装备变强、顾客被成功招待之间缺少直观连贯反馈。
4. 文档描述的完整玩法与用户实际感受到的内容存在差距，必须进行真人视角的端到端试玩验证。
5. 店铺内饰与顾客视觉主要是占位资源，角色动作和运动轨迹仍需实际画面审查。
6. 根目录快捷启动文件尚未更新为 0.2.2。
7. 旧零售系统仍有部分代码作为存档兼容层存在；清理时必须区分“兼容层”和“实际无用代码”，不能直接删除导致旧存档损坏。

## 下一任务建议顺序

### P0：恢复可信的可启动基线

1. 请用户正常关闭全部旧版 Hajimao DesktopShop 进程。
2. 将已验证的 0.2.2 EXE 更新到项目根目录。
3. 从根目录入口进行一次真实可视启动验收：街区实际可见、只有一个窗口实例、可拖动、置顶、吸附、穿透和店铺跳转正常。
4. 不得只验证进程存在；必须验证窗口实际有可见像素和可交互内容。

### P1：0.2.x 首次上手与正反馈小重做

1. 把首次体验收束为“看见顾客 → 毛毛投掷 → 招待成功 → 金币与商品掉落 → 明确提示装备提升”。
2. 街区只承担观察、收益和进店，不塞任务栏或长篇教程。
3. 店铺页突出当前收益、顾客需求、装备效果和首次掉落；删除不能帮助玩家做决定的装饰信息。
4. 用一次性、短句、场景内提示替代大段阅读。
5. 首次掉落、可装备升级、首次开店必须有清晰庆祝与前后数值比较。

### P2：运动和战斗表现

1. 为顾客定义进入、接近服务区、受击、成功离开和未满足离开的空间路径。
2. 为毛毛定义站位、朝向、预备、投掷、恢复和庆祝的动作状态机。
3. 核对所有 24 帧逻辑动作、产品挂点、骨骼锚点、整数像素定位和资源大小。
4. 用实际录屏或帧截图检查动画，而不是只依赖像素哈希测试。

### P3：内容与美术扩充

核心循环达到可理解、可持续挂机后，再扩充到至少 60 种商品、24 类顾客和更多事件，并逐店替换统一像素风内饰。

## 开发与验证工作流

1. 开始前阅读根目录 `AGENTS.md`。
2. 行为变更先写最小失败测试，再实现。
3. 开发中只运行聚焦测试。
4. 发布候选不再变更后，只运行一次完整测试：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test-all.ps1 -Configuration Release
```

5. 由 GitHub CI 作为独立第二门禁，不重复进行相同的本地审查。
6. 每版本只做一次变更日志、一次阶段审查、一次发布和一次清理。
7. GitHub 分支发布使用 `scripts/publish-github-branch.ps1` 或本地 `hajimao-fast-github` skill，避免重复慢速 push。
8. 发布后运行 `scripts/clean-workspace.ps1`，保留当前 Release，清除 `bin`、`obj` 和 staging。
