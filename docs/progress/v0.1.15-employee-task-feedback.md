# Hajimao DesktopShop 0.1.15 员工任务与岗位反馈阶段报告

## 结果

0.1.15 将员工从“按岗位播放固定路线”推进为“由真实经营状态选择任务”。经营模拟根据结账队列、正在结账的商品、采购在途订单、店铺清洁度、排班、体力和工资支付结果，为每名员工产生不可变任务快照；场景位置、员工卡片和对象详情共同消费这份快照。

游戏继续固定现实 `1x`，没有暂停、倍速或动画速度设置。离线挂机仍通过 `OfflineSettlementService` 批量调用同一个 `BusinessSimulation.AdvanceRealSeconds`，没有简化任务公式或额外收益捷径。

## 任务与岗位规则

- 任务类型：待命、休息、收银、补货、清洁、导购。
- 收银员：收银 → 导购 → 待命。
- 补货员：补货 → 导购 → 待命。
- 导购员：导购 → 补货 → 待命。
- 清洁员：清洁 → 导购 → 待命。
- 店长：收银 → 导购 → 清洁 → 补货 → 待命，作为专职员工缺位时的补岗角色。
- 采购员：补货 → 导购 → 待命。
- 收银和单个在途补货目标为独占任务；专职员工按稳定员工 ID 先领取，避免多人重复占用。
- 清洁和导购允许多人共同贡献，贡献继续使用每名员工的有效效率。
- 班外或体力耗尽的员工进入休息；体力耗尽后每分钟恢复 4‰，恢复到可工作状态后下一分钟返岗。
- 工资支付失败的员工当分钟待命，不贡献收银、清洁或导购效果。

## 真实经营接入

- 收银目标来自真实活动结账或队首商品；剩余时间使用结账状态中的实际分钟，首次领取时使用该员工效率计算。
- 补货目标来自当前店铺剩余时间最短的真实采购订单；目标货架由商品 `ShelfKind` 决定，剩余时间与采购订单一致。
- 清洁需求来自当前清洁度缺口；剩余时间按员工有效效率与实际每分钟恢复量向上取整。
- 导购贡献仅来自当前执行导购任务的已付薪员工；执行收银、补货或清洁时不会同时重复贡献服务。
- 当前任务不另存第二份可漂移状态，而是由已保存的经营队列、采购、排班和员工条件重新派生；SQLite schema 保持 v6。

## 任务驱动人物表现

- 收银任务在收银台区域活动。
- 补货任务根据常温、冷藏、冷冻目标走向对应货架。
- 清洁任务沿店铺地面巡视。
- 导购任务在顾客通道巡查。
- 休息任务固定在员工休息区；待命使用岗位稳定站位。
- 点击命中区域继续由同一个任务姿态编排器产生，不会出现人物位置与点击框漂移。
- 所有路线继续消费 24 帧逻辑时间轴和去重人物图集；Windows“减少动态效果”会冻结任务路线。

## 模块边界

- `EmployeeTaskPriorityCatalog` 只定义岗位规则，不接触经营状态或 WPF。
- `EmployeeTaskPlanner` 是纯 Application 决策函数，只接收员工可用性和店铺任务需求。
- `BusinessSimulation` 负责把真实状态转换为需求并应用选中的任务效果。
- `EmployeeOperationsService` 负责名册、排班、条件与只读快照，不持有店铺渲染状态。
- `BusinessShopEmployeeChoreography` 只将任务快照转换为像素位置，不修改经营状态。
- Desktop 的 `EmployeeTaskTextFormatter` 只负责中文展示；XAML 不包含经营判断或仓储规则。

## 保持不变

- 固定现实 `1x`；没有暂停、倍速或动画速度选择。
- 24 帧人物逻辑时间轴、8 个去重关键姿势和 24 KiB 图集预算不变。
- 多店共享资金、玩家等级、商品解锁、毛利、工资、采购、自动补货和日结规则继续生效。
- 街区长度仍由已开店铺数量决定且不设店铺数量上限；初始一家店仍只有一个店面宽度。
- schema v6 不变；本阶段不扩展签名、安装器、硬件矩阵或其他兼容/合规工作。

## 已知差距

- 岗位优先级目前是固定游戏规则，玩家还不能自定义单个员工的优先顺序。
- “补货”当前投影真实在途采购与目标货架；商品到达后仍直接进入现有货架库存模型，尚未建立后仓、搬运和上架的独立库存阶段。
- 店内继续最多显示四名员工；更多员工参与模拟和工资，但需要后续场景容量设计才能全部同时可见。
- 人物仍按岗位共享外观，没有按个体和店铺主题换装。
