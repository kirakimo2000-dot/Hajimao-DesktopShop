# 0.2.0 多店模拟与经营深度阶段总结

日期：2026-08-03
状态：完成

## 本阶段结果

- 所有已开店铺共享同一固定时间线，每个现实秒处理一个经营分钟。
- 店铺按 ID、员工按 ID 稳定排序；运行中开放的新店在下一 Tick 自动加入。
- 价格、服务、队列、整洁度、时段形成可解释需求分项，最终概率使用 0–10,000 整数基点。
- 顾客经历进店判断、商品选择、购买判断、结账排队和最终成交；失败结果进入逐店流失统计。
- 收银效率决定结账任务分钟，清洁效率决定恢复量，顾客到访持续消耗整洁度。
- 员工按排班分钟计费。工资不足时员工当分钟停工，现金、工时和费用不会部分提交。
- 共享钱包支付工资，各店独立记录工资成本与净利润。
- 每 1,440 个 Tick 生成逐店日结，包含客流、接受购买、成交、流失、收入、毛利、工资、净利润、整洁度和平均队列。

## 模块边界

- `Domain/Demand` 只负责输入校验与需求公式。
- `Domain/Employees` 预览/提交精确分钟工资；`RetailBusiness` 原子编排钱包、员工和店铺费用。
- `Application/Business/Simulation` 只通过 `BusinessGameService` 命令和不可变快照运行多店，不持有店铺聚合引用。
- WPF、Rendering、Infrastructure 没有取得新玩法规则；SQLite schema 保持 v2。

## 验证证据

- `dotnet test HajimaoDesktopShop.slnx -c Release`：102 passed，0 failed。
- `dotnet build HajimaoDesktopShop.slnx -c Release --no-restore`：0 warnings，0 errors。
- 10 个项目执行直接与传递依赖漏洞审计：无已知 NuGet 漏洞。
- 双店 30 日（43,200 Tick）使用相同种子运行两次，现金与所有逐店运营指标一致且保持边界有效。
- 活跃源码扫描确认没有重新引入暂停、2x、4x或玩家速度控制。

## 已知边界

- 新多店模拟尚未接入当前原型 WPF 组合根，因此 0.2 以可测试玩法 API 交付，不新增半成品页面。
- 多店、员工、队列、整洁度和日结尚未进入 SQLite；不能把 0.2 快照误报为已经持久化。
- 当前员工视为已排班，每个 Tick 都产生工资；招聘、排班、休息和满意度属于 0.5。
- 需求系数是第一套确定性基线，后续需用长期模拟和试玩数据继续平衡。
